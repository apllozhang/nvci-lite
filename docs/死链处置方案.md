# 21 条确认死链处置方案（待用户拍板）

> 对应 HANDOVER 第 5 节第 1 项。本文只出方案，**未改代码、未动生产数据**。
> 证据在 NAS `data/probe-state.json`：H3C 404×18、ALE AP1521 重定向环、2 份损坏 PDF。

## 1. 现状：人工兜底通道已经存在

HANDOVER 候选里的「提供人工 PDF 上传通道」**不是待建功能**，第 5 步「彩页校验 → 人工校验」弹窗与批量导入已经具备：

| 能力 | 入口 | 后端 |
|---|---|---|
| 立即重测 | 人工校验弹窗 | `POST /api/probe/retry` |
| 修正官网链接 | 弹窗「修正链接」 | `POST /api/probe/manual/:id/url`（HTTPS，`allowManualUrl`） |
| 单条 PDF 上传 | 弹窗「上传本机下载的 PDF」 | `POST /api/probe/manual/:id/pdf`（签名/页数/SHA-256 建档） |
| 批量 PDF 导入 | 第 5 步「批量导入」 | 文件名匹配 → 逐条上传校验 |
| 人工裁定 | 弹窗「人工裁定」 | `manual_ok` / `manual_invalid` / `paused`；裁定后自动巡检跳过 |

因此真正要定的不是「要不要做上传」，而是：**这 21 条要不要人工消化，以及用哪条路消化**。

## 2. 两案对比

### 案 A：保持异常标记，不做人工消化（维持现状）

**做什么**：业务侧继续在第 5 步按状态筛「资源不可用」；不上传、不改链接、不裁定。

| 维度 | 评估 |
|---|---|
| 代码改动 | **0** |
| 产品改动 | **0** |
| 数据改动 | **0** |
| 人工成本 | 每次选型要绕开这 21 条；对比矩阵可能长期缺 H3C 部分型号 |
| 风险 | 误把「厂商已下线」和「链接暂时抖动」混在一起；采购结论缺证据链 |
| 适合场景 | 这 21 条对应的型号短期不进选型；或等 H3C 官网改版后再统一补 |

**建议操作（若选 A）**：对确认永久失效的条目打 `manual_invalid`（带备注「官网 404，待新彩页」），让自动巡检跳过、告警降噪；暂时不确定的先留 `unreachable`。

### 案 B：用现有通道人工消化（推荐，但要排期）

**做什么**：对 21 条按归因分流，**不写新代码**：

1. **H3C 404×18**：官网搜新 URL → 弹窗「修正链接」；找不到新 URL 时浏览器下载 PDF → 单条/批量上传建档。
2. **ALE AP1521 重定向环**：同上，优先找新直链；实在无公开彩页则 `manual_invalid`。
3. **损坏 PDF×2**：重新下载上传；若官网文件本身损坏，`manual_invalid` 并备注。

| 维度 | 评估 |
|---|---|
| 代码改动 | **0**（通道已齐） |
| 产品改动 | **0** |
| 数据改动 | 生产 `probe-state.json` + 缓存；SHA-256 建档与四态语义不变 |
| 人工成本 | 约 1–2 小时（搜链接/下载/上传/裁定）；需内网能访问 8789 |
| 风险 | 人工改链接时只允许 HTTPS，仍受重定向白名单断言；上传与自动采集同一校验门禁 |
| 适合场景 | 这批型号还会进对比选型 |

**不推荐现在做的增强**（除非你点名）：

- 死链「一键批量裁定」：容易误标 `manual_invalid`，违背「先归因再处置」。
- 为死链单独开「非官网镜像」采集：**撞合规红线**，除非你明确扩展白名单范围。

## 3. 决策建议

我更倾向 **案 B 的分流操作**，理由：

1. 通道已经验收过（单测 + 生产界面），再做新上传功能是重复建设。
2. 21 条里 18 条同属 H3C 404，大概率是一次官网改版，找新链比永久放弃划算。
3. 损坏 PDF 和重定向环用上传/改链即可闭环，不需要改采集方法论。

**建议你拍板时直接选一个**：

- **B1（推荐）**：我按归因逐条处理，处理完出清单（每条：原 URL / 新 URL 或上传 SHA / 终态）。
- **B2**：只把「确认无替代」的几条标 `manual_invalid`，其余暂不动，等 H3C 官网稳定后再批量找链。
- **A**：全部维持异常，仅在选型时人工绕开。
